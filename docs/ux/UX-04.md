## Flow and local preview

```text
Devices / empty inventory
  -> Add device
  -> Device name + optional site/model
  -> Create device
     -> Confirmed: device detail, Not enrolled, no observation
        -> Onboarding guidance -> future approved agent enrollment
     -> Rejected / forbidden / expired: no demo record added
     -> Unknown: lock submission -> check original outcome
        -> Created: open that record once
        -> Not created: allow editing and retry
        -> Still unknown: retain pending state
```

The [local prototype](prototype/index.html?variant=A&screen=devices) uses the
existing A fleet sidebar, B operations board and C device workbench, with the
same creation flow. Open the HTML file directly, or run from the repository root:

```sh
python3 -m http.server 8765 --bind 127.0.0.1 --directory docs/ux/prototype
```

Then visit `http://127.0.0.1:8765/?variant=A&screen=devices`. B/C remain selectable
in the bottom switcher. `?variant=A&screen=add` opens the form directly. Stop the
optional server with Ctrl-C. Keep the preview local; no production route exists.

## Form, results and inventory behavior

| Item | Proposed interaction |
| --- | --- |
| Device name | Required display label; whitespace-only values rejected. Names need not be unique in this demo; a name does not prove device identity. |
| Site / model | Optional display metadata; blank values show Not specified. |
| Demo input limits | 120 characters per field for bounded review input, not a selected API/schema limit. |
| Record ID | Generated `demo-new-…` identifier for the local fixture; no user-supplied identity, address, credential or host key. Actual identifier design is unresolved. |
| Cancel | Returns to inventory without adding a record; no enrollment or device action. |
| Confirmed creation | Adds one invented record, selects it and opens detail. Search/filter reset so returning to the last inventory page reveals the new item. |
| New record state | Enrollment: Not enrolled; observation: Unknown; last seen: No observation available. No SSH access is granted. |
| Rejected / forbidden / expired | Explicit simulated result, no addition; retain safe invented input. These are review examples, not implemented authorization/session enforcement. |
| Unknown result | Freeze the submitted draft and block another submission; Add device returns to the unresolved draft even after navigation. Simulated lookup decides created/not-created/still-unknown. |
| Layout changes | Preserve the draft and pending state. Native input arrow keys retain their behavior. |
| Empty inventory | On Devices choose the empty scenario, then Add device to an empty demo inventory. This deliberately clears local device fixtures before opening the form, so the first record is truly created from zero. Reload restores the original fixtures. |

All mutations, drafts and lookup outcomes live in memory and disappear on reload.
The pending lock applies within that page lifetime only; reload is not production
reconciliation. Inventory counts/attention summaries derive from the current local
array. The three fixed audit examples remain historical synthetic examples; this
prototype does not emit authoritative creation audit events. The state disclosure
shows the draft, pending request and current inventory for design review; enter
invented data only.

## Enrollment and backend handoff

Creating metadata is a separate step before binding the actual device/agent.
The [UX-01 journey](UX-01.md#2-onboard-a-device) now starts at Devices rather than
requiring an existing device. [UX-03](UX-03.md#screen-and-state-handoff) retains
its review gate. Device detail offers onboarding guidance; the existing pending
enrollment example does not change the new record to enrolled or online.

The [WEB-01a inventory](../web/WEB-01a.md) identifies no device application store
or creation API. WEB-01/M02 must decide creation authority/resource scope,
identifier/field validation, persistence, audit, concurrency/duplicate protection,
reconciliation and subsequent identity binding before implementation. User-entered
model/name/site cannot authenticate a device. Pairing code/QR/token delivery,
installation/enrollment commands and host-key trust remain unresolved; this flow
chooses none. [AGENTS.md](../../AGENTS.md) and [ADR-001](../adr/ADR-001-foundation.md)
still require human approval of contract/security changes. M01/M02 acceptance and
production dashboard gates are unchanged.

## Review, evidence, impact and rollback

Human review is pending: create a record in A/B/C, repeat from zero devices,
cancel, submit whitespace, inspect failure/denied/expired outcomes, preserve a draft
across layout switches and reconcile an unknown response without a second record.
Inspect long names, markup-like text, narrow view/zoom, keyboard focus, form labels,
result announcements and the return to inventory. Confirm that created, enrolled,
online and authorized-for-SSH remain distinct. No human browser check is inferred
from the owner's request.

Follow-up [#39](https://github.com/LiiWzz/DeviceBridge/issues/39), primary source
branch `fix/ux-04-creation-focus`, removes the second render after successful
creation. Navigation receives the creation status before rendering and focusing
the detail view. Direct creation and reconciliation share this path. Captured
[follow-up evidence](evidence/ux-04/focus-validation.txt) checks a single final
render with focus requested in A/B/C; actual browser focus remains unverified.
This reduces one redundant render without measured performance claims. The
existing security boundaries, hardware limitations and rollback steps below
also apply to this local prototype follow-up.

Evidence-only follow-up [#41](https://github.com/LiiWzz/DeviceBridge/issues/41)
on `docs/ux-04-focus-evidence` completes the
[historical before/after matrix](evidence/ux-04/focus-matrix.txt) for direct and
reconciled creation in A/B/C. Every historical case reproduces two renders;
every fixed case requests focus on its single final render. Historical diagnostic
success means the known defect was reproduced, not that browser focus passed.
This adds no runtime or security-policy change and has no device/resource impact;
rollback is a reviewed revert of these documentation additions. Browser focus,
accessibility, unsupported toolchains and physical ARM validation remain unverified.

Exact executed commands/output and temporary diagnostic source are captured in
[validation.txt](evidence/ux-04/validation.txt) and
[secrets.txt](evidence/ux-04/secrets.txt). Node VM output checks use a DOM stub;
they cannot verify browser layout, CSP enforcement, native validation, focus,
responsive behavior or accessibility. BrowserOS neo tools are unavailable in this
session; no real-browser validation is claimed. No new application builds,
integration/security acceptance, Windows/ARM toolchain execution or physical ARM
measurements are claimed. Pattern scanning cannot guarantee no secrets exist.

This local throwaway change adds no backend request, persistent storage, runtime
dependency, agent allocation, flash write, root privilege or production config.
User text is escaped on rendering; existing CSP and loopback/file preview guards
remain. Small local arrays are for review only; no 100-device performance result
is established. Production UI must be rewritten after the relevant approvals.

Rollback: close/reload the preview or stop the optional local server. Supersede
the feature branch/PR, or use a reviewed revert PR into `develop` after a human
manual merge, retaining requirement provenance. No service, device, credential or
database state changes. No merge, self-approval or auto-merge is authorized.
