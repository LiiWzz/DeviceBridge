## Question and local preview

[UX-04](UX-04.md) extends this prototype with creation of a new device record
from Devices or an empty inventory, followed by onboarding. Its primary source
is `feat/ux-04-add-device`; the original UX-02 branch remains unchanged. The
owner requested the new entry flow; its detailed interactions await human review.

Which hierarchy best supports finding a device and understanding whether access
is possible: fleet navigation, an attention-first board or a device workbench?
The Matt Pocock prototype skill's UI workflow supplies three structurally distinct
variants. There is no existing web application or routing convention to embed
them in; the throwaway files sit beside the UX documents.

Open [prototype/index.html](prototype/index.html) directly, or from the repository
root run:

```sh
python3 -m http.server 8765 --bind 127.0.0.1 --directory docs/ux/prototype
```

Then open `http://127.0.0.1:8765/?variant=A`. No install, build or external assets.
Stop the server with Ctrl-C. The preview refuses to render on non-local hostnames.
This is a convenience guard, not a production security boundary. There is no
production build or deployment target for this artifact; keep the prototype on
its feature branch as the design primary source. Do not publish it as a dashboard.

| URL variant | Structural choice | Review trade-off |
| --- | --- | --- |
| `?variant=A` | Persistent fleet sidebar; counts first, then attention and recent requests | Predictable global navigation; extra step to device context |
| `?variant=B` | Horizontal navigation and persistent attention strip; queue before counts | Focus on exceptions; more space given to operational triage |
| `?variant=C` | Persistent device rail with workspace tabs; selected device first | Device context stays prominent; narrow screens need horizontal device scrolling |

The floating bottom switcher and Left/Right keys cycle layouts with wrapping.
Typing, selects, editable content and open dialogs retain their arrow keys.
`variant` and `screen` are URL parameters; filters, selected device, scenario and
results are memory only and reset on reload. State is visible in a disclosure
below each page. Layout switches preserve in-memory review context.

## Screen and flow coverage

The initial fixtures contain six invented devices and three invented events. Fixed times
use UTC; counts derive from this same device set. No record comes from a service,
and none establishes live availability. Terms and fields illustrate UX-01 and the
[roadmap](../ROADMAP.md); WEB-01 must settle their actual semantics.

| Area | Clickable review path | Failure / uncertainty example |
| --- | --- | --- |
| Sign-in | Sign-in → enter synthetic workspace | Expired session and access-denied examples; no credential form or selected provider |
| Overview | Observation count → filtered Devices; attention item → detail | Unknown vs offline, stale historical observations, unavailable counts |
| Devices | Search name/ID/site → filter → page → detail → return | No matches distinct from empty authorized inventory; query, filter and page retained on return |
| Detail/onboarding | Select offline/unknown device → onboarding → pending; revoke → cancel or simulated result | Identity/connectivity separation; rejected, unknown and confirmed revocation; no live changes |
| Sessions | Access request preview → denied/expired/revoked/unavailable/handoff guidance | No connected-session claim, executable CLI syntax or bypass for host-key verification |
| Users/permissions | Capability discussion table → permission-change confirmation | No roles or grants selected; rejection and uncertain results, no self-escalation implementation |
| Audit | Filter actor/device/action/date/result → clear filters | Empty matches vs unavailable history; missing evidence does not prove no event |

Every page has explicit scenario controls for loading, empty, error, expired,
forbidden and stale. These are review controls, not an authorization mechanism.
Forbidden/expired/loading/error/empty views withhold the normal screen content.
The selected device rail and operations summary contain synthetic context;
their behavior on real authorization loss remains a WEB-01 disclosure question.
Onboarding illustrates pending enrollment; lost-response outcomes require
authoritative reconciliation before retry. Revocation does not promise immediate
termination of existing sessions.

Desktop layouts collapse below 850 CSS pixels: sidebar becomes horizontal
navigation, workbench rail becomes a horizontal selector, split panels stack,
and tables scroll within their container. Buttons and labels use text rather
than color alone. Skip navigation, visible focus, native dialogs, initial Cancel
focus, focus restoration and live result announcements are included for review.
WCAG conformance, actual keyboard operation, contrast, mobile appearance and
assistive-technology behavior require browser/human evidence; inclusion of these
elements does not establish their acceptance.

## Human flow review record

The owner replied **“A”** to the explicit conversation question offering flow
approval and layout A (fleet sidebar), alongside B/C and a request-changes option.
This clears UX-03 discovery only. Rationale, exact response time, browser/viewport
and executed human browser checks were not supplied; no GitHub review or security
approval is inferred. See the [UX-03 decision record](UX-03.md#decision-and-primary-source).

Use all three variants at desktop and a narrow viewport (for example 390 pixels):

1. Find North pump station, then an offline and an unknown device. Search for no
   matches, page through all devices, open detail and return with filters intact.
2. Open onboarding and inspect pending enrollment. Confirm it never presents a
   token or equates local configuration with enrollment.
3. Inspect denied, expired, revoked, unavailable and CLI handoff examples. Verify
   no browser shell, executable invented command or key upload is offered.
4. Open revoke and permission confirmations. Cancel with the button and Escape;
   verify return focus. Inspect unknown/rejected/confirmed outcomes and distinguish
   future request rejection from existing-session effects.
5. Filter audit examples, then select empty, error and stale states. Check whether
   the operator can explain missing evidence without assuming success.
6. Use keyboard-only navigation and the layout switcher. Check focus visibility,
   labels, table access, narrow layout, zoom and non-color status text.

The choice is captured in the UX-03 issue and decision record. Keep all variants on this
prototype branch; future approved production UI needs a separate implementation
under WEB-02+ and must not promote this throwaway code directly.

## Validation, implications and rollback

Exact executed commands and outputs are in [validation.txt](evidence/ux-02/validation.txt)
and [secrets.txt](evidence/ux-02/secrets.txt). Script syntax, rendered-output smoke
checks and static document/asset checks are distinct from browser evidence.
BrowserOS neo tools are unavailable in this session; no real browser, screenshot,
responsive/keyboard/a11y or human flow validation is claimed. Physical ARM hardware
is unavailable, ARM toolchains and Windows execution are not validated, and no
application build/integration suite is rerun for this isolated browser prototype.

No runtime dependency, agent allocation, flash write or root requirement is added.
Small fixtures render locally; no refresh loop, backend request, persistent store,
analytics, cookies or service worker is used. The CSP blocks connections, forms,
frames/resources by default; scripts/styles load only from local files. No auth,
permission or audit enforcement is implemented or approved. Text inputs are escaped
before HTML rendering. Scenario outcomes are synthetic, including confirmations.
Resource measurements and a 100-device fleet acceptance remain WEB-01/02/05 work.

Rollback: stop the optional local server; discard in-memory state by closing the
page. Supersede the branch/PR or use a reviewed revert PR into `develop` if its
documentation is merged. No database, credential, production service or device
state changes. Preserve the UX-01 approval provenance when superseding the packet.
