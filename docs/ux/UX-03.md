## Navigation and responsive structure

```text
Fleet shell
  Skip to main content
  Persistent sidebar: Overview / Devices / Sessions / Users / Audit
  Main: page title, scope/freshness, primary action, content and results
    Devices -> detail -> onboarding / revoke confirmation
  Sign-in / expired / denied: protected content withheld
```

Use the same navigation order on every management screen, with a text label and
current-page indication independent of color. A device detail belongs under
Devices. Sign-in is an entry view, not a fleet navigation item. Do not retain the
prototype variant switcher, scenario controls or synthetic context in production.

Proposed dimensions are CSS pixels with rem-based text and spacing implementation:

| View | Structure | Overflow and context |
| --- | --- | --- |
| Above 850 px | 220 px sidebar; main fills remaining width up to 1400 px; 32 px main padding | Sidebar follows document scroll; no nested full-page scroll pane |
| 850 px and below | Brand then labeled horizontal navigation, main below; 16 px main padding; panels stack | Navigation scrolls within its own region; current item remains discoverable |
| Narrow view / zoom | One content column; toolbars wrap; full-width inputs where needed | Page content fits 320 px; wide data tables alone may scroll horizontally |

The 850 px breakpoint is a proposal from A's prototype, subject to content and
zoom testing. No fixed footer may obscure focus or results. Long names/IDs wrap
or remain accessible in a labeled scroll region; avoid tooltip-only full values.
Preserve search/filter/page when returning from detail. Production URL storage,
safe sign-in return and authorization-loss handling await WEB-01; never put
credentials or sensitive form content in URLs.

## Visual tokens

Use local system fonts: `system-ui, -apple-system, sans-serif`; monospace only
for identifiers and diagnostic text. No downloaded font is required. Body text
is 1 rem with line-height 1.5; supporting text 0.875 rem / 1.5; table headings
0.875 rem / 1.4; section headings 1.25 rem / 1.3; page titles 2 rem / 1.2,
reducing to 1.75 rem on narrow layouts. Allow text expansion and wrapping.
Use sentence case and visible units/time zone; timestamps need freshness context.

Spacing scale: 4, 8, 12, 16, 24, 32, 48 px equivalents in rem. Form controls and
buttons have a proposed minimum 44 by 44 px interaction area; neighboring actions
have at least 8 px separation. Use 8 px control radius, 12 px panel radius,
1 px decorative dividers and 2 px control boundaries. Shadows are optional
decoration, never the only indicator of state or focus.

These tokens are prescribed as opaque color pairs; opacity, gradients and images
require fresh contrast verification. The checker records calculated ratios in
[validation.txt](evidence/ux-03/validation.txt). Adopt a design acceptance floor
of 4.5:1 for all listed text pairs and 3:1 for listed control/focus pairs. This
calculation is partial evidence toward the roadmap's planned WCAG 2.2 AA target;
it does not establish conformance or browser rendering results.

## Reusable presentation and behavior

| Element | Required behavior and content | Keyboard / focus |
| --- | --- | --- |
| Navigation | One consistent shell, labeled links, current-page marker, skip link | Natural document order; skip moves focus to main; route changes focus page heading; back restores meaningful context |
| Page heading | One main heading; authorized scope and freshness near counts | Heading structure follows document order; no focus change on background refresh |
| Status | Text plus optional icon; observation, freshness and access permission separate | Meaning available without color, hover or animation |
| Data table | Caption, semantic headers, labeled row actions, visible result count, pagination | Native table semantics; no custom arrow-key grid; keyboard-accessible labeled scroll region where needed |
| Search / filters | Persistent visible labels, clear action, retained query; reset page on changed criteria | Enter or explicit Apply submits; announce result count once; keep focus on initiating control |
| Pagination | Previous/Next, current page and known result scope; unavailable buttons explained | Native buttons/links; focus remains stable on page change; no unexpected navigation |
| Form | Visible label, help, required indication, inline errors linked to fields; entered non-sensitive values retained on error | Submit focuses error summary linking to invalid fields; no placeholder-only labels or unsolicited focus moves |
| Confirmation dialog | Title, target identity, scope/consequences, Cancel and explicit action verb; unknown effects stated | Modal focus containment; initial Cancel; Escape cancels before submission; close restores trigger or logical successor |
| Submitted mutation | Pending result, duplicate UI submissions prevented, authoritative result required | Announce pending/result without repeated alerts; keep result visible; closing UI does not imply request cancellation |
| Result notice | Confirmed, rejected and unknown are different; retry only through approved reconciliation | Nonurgent live status; urgent errors announced once; no success based only on local click |

These are UX responsibilities, not authorization guarantees. Server enforcement,
idempotency, allowed retry, protected return URLs and audit events require approved
contracts. If the connection is lost after submission, show unknown outcome and
approved reconciliation guidance; do not offer blind destructive retries.

## Screen and state handoff

The owner's later clarification requires Add device from Devices and empty
inventory before onboarding an existing record. See the proposed
[UX-04 creation handoff](UX-04.md) for form fields, mutation outcomes and the
separate record/enrollment/connectivity states. This extends discovery inputs;
it does not approve new backend contracts or the UX-03 packet.

Every data view distinguishes loading, empty inventory, no matches, error,
forbidden, expired and stale states where applicable. Loading keeps headings and
announces progress without showing placeholder counts as real data. Error offers
an approved retry and preserves safe input. Empty shows a permitted next step;
no matches offers clearing filters. Forbidden/expired withhold protected content,
including navigation summaries and cached metadata as required by the eventual
disclosure policy. UX-02's fixed synthetic rail is not a production precedent.

| Screen | A layout content and required state examples | Backend/design dependency |
| --- | --- | --- |
| Sign-in | Entry, denied, expired and provider unavailable; safe next step | Provider, logout/session design and safe return at WEB-01; no invented credential form |
| Overview | Authorized counts first, then attention and recent requests; unavailable counts use explicit unknown display | Authorized inventory, observation/freshness semantics; health probes cannot supply these |
| Devices | Search/filter, table, pagination, retained return context; offline/unknown rows remain distinct | Approved metadata, query/page and disclosure rules |
| Detail / onboarding | Identity before connectivity; observation time; pending enrollment; cancel/reject/unknown/confirmed revoke | Approved M02 identity/lifecycle, WEB-01 actions and audit; no tokens or runnable invented commands |
| Sessions | Request/history distinction; deny/expiry/revoked/unavailable; native CLI guidance | Accepted M02 authorization and host-key verification; no browser terminal/key upload; termination only if separately supported |
| Users / permissions | Capability separation and scoped explanations; confirm changes; denied/conflict/unknown | Approved role/grant/admin model; UX-01 matrix grants no authority |
| Audit | Actor/device/action/time/result filters, redacted records; empty vs unavailable history | Approved visibility, event fields and retention; absent history does not prove no event |

Online observation does not grant connection rights. Stale records cannot imply
current availability. Revocation confirmation must distinguish future requests
from existing-session effects without promising immediate termination. Use only
authoritative events for completion and session connection claims.

## Implementation responsibilities and acceptance

The future frontend should put shared navigation, focus management and data-state
presentation behind small module interfaces rather than repeating behavior on
each screen. Do not create speculative framework abstractions here. Select the
framework/hosting and implementation interfaces in WEB-02 with rationale. No new
runtime, package manifest or production route is part of UX-03.

| Gate / deliverable | Owner | Required evidence / current state |
| --- | --- | --- |
| UX-03 design review | Human owner / UX | Approve navigation, tokens, states and interaction rules or request changes; pending |
| WEB-01 contracts | Backend / Security / Architect | M02 identity agreement, API/schema/errors/auth/session/permissions/audit ADRs and Tech Lead approval; pending |
| WEB-02 foundation | Frontend / Backend | UX-03 approval, WEB-01 approval and M02 acceptance; choose stack, implement shared behavior and API client separately |
| WEB-03/04 screens | Frontend / Backend | Dependency-ordered issues, accepted matching APIs; trace each row above to working/negative cases |
| WEB-05 validation | QA / Security / DevOps | Browser/keyboard/assistive tech, direct authorization-negative tests, resource measurements and rollback runbook; pending |

Implementation review must record browser/version/OS, viewport (including 390 px
and 320 px), text enlargement/zoom, keyboard traversal and focus return for list,
detail, pagination and dialogs. Include screen reader names/versions and observed
labels/status announcements, contrast for all rendered states, long identifiers,
empty/error/denied/expired/stale data, lost responses and unauthorized direct
resource access. Automated checks complement human evidence; none are claimed
as passed here. No motion is required; any later animation must respect reduced
motion and avoid conveying essential information solely through motion.

subject to ADR and human approval. No backend or production deployment is changed.
