## Operator goals and information architecture

An operator needs to identify the intended device, assess information freshness,
request permitted native SSH access and understand failures. A person responsible
for fleet access needs reviewed onboarding/revocation flows and an auditable
explanation of changes. These are tasks, not selected application roles.

```text
Entry: sign-in / access denied / session expired
Management shell
  Overview
  Devices
    Device detail
      Onboarding guidance / revoke-access confirmation and result
  Sessions
    Session detail / native CLI handoff guidance
  Users and permissions
  Audit history
```

Navigation visibility helps explain permissions; backend authorization must
enforce every action and direct link. Routes, metadata fields, authentication,
session lifecycle, refresh cadence and permission representation belong to
WEB-01 and approved ADRs. They cannot be inferred from this tree.

## Journeys for human review

### 1. Find a device

1. Enter the proposed authenticated shell and open authorized Devices results.
2. Search/filter/page, open detail and retain enough context to return to results.
3. Compare identifying metadata and last-seen context before requesting access.
4. Distinguish no matches from no authorized inventory and service failure. Offer
   clearing filters for no matches; use the approved disclosure policy for
   forbidden/missing detail without leaking unauthorized metadata.
5. Label stale and unavailable data explicitly. Old online data cannot establish
   current reachability; unknown cannot silently become offline.

Review outcome: the operator distinguishes wrong device, empty search, offline,
unknown, stale data and failed retrieval. Exact status/disclosure semantics are
WEB-01 questions, as required by the roadmap's freshness and security validation.

### 2. Onboard a device

1. An authorized operator opens onboarding guidance and verifies intended device
   identity and prerequisites under the future approved M02 design.
2. Present only approved enrollment instructions. Credential delivery/bootstrap
   and recovery remain unresolved; this proposal supplies no token, executable
   command or default credential.
3. Distinguish pending enrollment, confirmed enrollment and current connectivity.
   Explain denied, expired and unavailable outcomes using the approved next step.
4. After connection loss or an ambiguous submission, reconcile authoritative state
   before offering repeat submission. Duplicate/replay behavior awaits WEB-01.

Review outcome: local health/config success is never mistaken for enrollment.
Credential lifecycle questions remain those of the
[security baseline](../../security/README.md#proposed-credential-and-token-lifecycle--unimplemented).

### 3. Request native SSH access

1. From the intended device detail, inspect context and request access through
   the future approved authorization flow. Online status is no access grant.
2. Explain denied/expired/revoked requests and service unavailability without an
   authentication workaround.
3. Present native CLI handoff only after its interface is approved. Keep credentials
   out of commands, URLs and clipboard guidance; provide no invented CLI syntax.
4. Require the accepted native client to verify the SSH host key. A mismatch must
   not offer an ignore-verification shortcut. Show connected only when supported
   by authoritative session evidence.
5. Inspect outcomes in permitted session history. Browser terminal and private
   SSH key upload/storage are outside the roadmap's MVP.

Review outcome: request, authorization, CLI handoff and connected session remain
distinct. The existing CLI cannot establish any of those remote states.

### 4. Revoke access

1. An operator with separately approved authority reviews the target and known
   consequences in an explicit confirmation.
2. Recheck authorization server-side on submission. Guard duplicate submissions
   through the approved contract; hiding controls supplies no enforcement.
3. Show confirmed, rejected or unknown outcome. If a response is lost, reconcile
   authoritative state before retrying or declaring completion.
4. Distinguish rejection of future requests from effects on existing sessions.
   Propagation timing and termination remain M02/WEB-01 decisions; promise no
   immediate disconnect or particular time bound here.
5. Present audit evidence only when the service supplies it. An unavailable audit
   view cannot establish success. Recovery must never silently restore revoked
   identity; it requires the approved lifecycle flow.

Review outcome: target, scope and uncertainty are explicit. The
[security baseline](../../security/README.md) leaves active-session and outage
semantics for approved contract work.

### 5. Inspect audit history

1. Open the permitted view and filter approved actor/device/action/time/result
   dimensions from the roadmap.
2. Inspect permitted context; distinguish attempted/denied/completed outcomes
   according to the eventual audit contract.
3. Keep credentials and unauthorized metadata out of results, links and alternate
   direct queries. No audit export or retention duration is selected here.
4. Distinguish empty results from unavailable history/query failure; show time
   context. Missing evidence does not establish that no event occurred.

Review outcome: the operator can trace an event and recognize evidence gaps.
Fields, visibility, retention and integrity mechanisms remain WEB-01 decisions.

## Draft permission discussion matrix

This matrix inventories required capability decisions; it grants no permission
and defines no roles. All grants, resource scopes and role mappings remain TBD in
approved contracts. It derives from the roadmap's permission and security gates.

| Task / capability | Scope constraint to resolve | Denied/unavailable experience | Approval / blocker |
| --- | --- | --- | --- |
| View devices/status | Authorized device subset and allowed metadata | No unauthorized detail; distinguish unavailable inventory | WEB-01 inventory/disclosure rules |
| Request native SSH | Separately authorized user/device/session; viewing implies no connection right | Denied/expired/revoked vs unavailable; no fallback | Accepted M02 grants and host-key flow |
| Inspect sessions | Own vs others' records; device scope | No leaked session metadata; explicit failed retrieval | WEB-01 visibility model |
| Enroll a device | Explicit enrollment authority and target identity | Denied/expired/pending/unknown results | M02 bootstrap/identity and audit contracts |
| Revoke access | Separately authorized target/scope; active-session effects unresolved | Confirmation, rejected/confirmed/unknown result | M02 revocation policy and WEB-01 admin APIs |
| Change user permissions | Separate administrative authority; self-escalation controls unresolved | Forbidden/conflict/unknown result | WEB-01 role/scope/admin/audit design |
| Inspect audit history | Independently authorized records and redacted fields | Empty vs unavailable; no alternate-query disclosure | WEB-01 visibility/retention contract |
| Terminate session, if supported | Own/other session authority separately decided | Confirmation and authoritative outcome | Backend enforcement/audit support and approved policy |

Viewing does not imply connecting; connecting does not imply administration;
administration does not imply unrestricted SSH or audit access. Backend enforcement
must apply to actions and resource IDs, including direct API calls. Authentication,
expired/revoked access and control outages follow the approved fail-closed design.
[AGENTS.md](../../AGENTS.md) requires an ADR and Tech Lead approval before changes
to contracts/security policy; this matrix supplies review questions only.
